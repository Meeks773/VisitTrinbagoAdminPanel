## Verified CMS interface

The owner supplied the public VisitTrinbagoAdminPanel repository and spreadsheet-import documentation. The spreadsheet import creates new drafts and skips existing listings; it must not be used for this photo attachment job.

The inspected CMS source has:

- Session-based admin authentication; no API-key or Bearer-token importer.
- `GET /api/listings/:id` and photo-only `PATCH /api/listings/:id`.
- `POST /api/uploads/request-url`, followed by a raw PUT to its signed upload URL.
- Persistent object references in `featuredImage` and `galleryImages`; no existing typed card/detail variant contract.

`galleryImages` PATCH replaces the array. Refresh before applying approved changes; deliberately merge rather than discarding existing galleries. There is no compare-and-swap protection, so a proper CMS-side import transaction or conflict check is needed to prevent concurrent edits being overwritten. Uploaded objects and listing PATCHes are not one atomic operation.

## Safety issues before live bulk use

The inspected public repository contains hardcoded admin authentication credentials. Their values were not copied, used, or saved. The CMS owner should rotate them and move authentication secrets out of source control.

The inspected upload-signing route is registered before admin authentication, and the object-serving route lacks an access check. Do not interpret an anonymous endpoint as permission to use it. Do not upload originals assuming a “private” storage prefix makes the serving URL private. Protect upload issuance and implement enforceable separation between private originals and public display copies in the CMS project.

These findings describe inspected repository code, not a penetration test or proof that the deployed revision is identical. No unauthorized credential or write tests were performed.
